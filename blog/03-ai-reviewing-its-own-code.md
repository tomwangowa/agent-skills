# AI Review 自己的 Code，會發生什麼事？

> *這是「當 AI 越來越好用，品質反而越來越差」系列的第 3 篇。*
> *這一篇講的是：為什麼我讓 Gemini 來審 Claude 的 code，以及兩個 AI 吵架時會發生什麼好事。*

---

寫完 code 之後做 code review，這是工程師的基本功。所以當我開始大量用 Claude Code 寫程式，我自然也會請它「review 一下剛才寫的」。

它確實會找到問題。命名不一致、缺少 error handling、可以抽成共用函式的地方——這些它都抓得到。不是完全沒用。

但慢慢地我注意到一個 pattern：**它找到的問題，永遠在安全範圍內。**

它會挑實作層面的毛病——變數名稱、edge case、防禦性不足。但「這個設計方向對不對」「這個架構選擇有沒有問題」——這一類碰觸核心決策的質疑，從來不會出現。

這也合理。就像你問一個作者「你這段寫得好不好」，他多半會告訴你哪裡可以潤一潤，但不會說「整段砍掉重寫比較好」。

---

## 找一個更挑剔的 Reviewer

在真實團隊裡，我們不會讓寫 code 的人做唯一的 reviewer。不是因為不信任——而是因為作者天然有盲區。你在寫的時候做了十個微決策，每個都有你當下的理由，但 reviewer 的價值就是用一雙沒有那些包袱的眼睛重新看一遍。

所以我做了一個當時看起來有點荒謬（也可以說是前衛）的決定：**讓 Gemini 來 review Claude 寫的 code。**

不是因為 Gemini 比 Claude 聰明。而是因為 Gemini 對這段 code 沒有感情。它沒有參與設計、沒有做過那些微決策、不需要為任何選擇辯護。它就是一個冷冰冰的第三方，看到什麼說什麼。

這就是 `code-review-gemini` 這個 skill 的由來。

---

## Gemini 是一個非常挑剔的 Reviewer

第一次跑 Gemini review 的時候，我有點被嚇到。

同樣的一段 code，Claude 自己 review 覺得還不錯、提了幾個小建議。Gemini 看完列了一串問題——邊界條件、error handling 的漏洞、潛在的邏輯問題。它挑毛病的力道，遠超我的預期。

但真正有趣的不是 Gemini 找到了什麼，而是**接下來 Claude 怎麼回應**。

Claude Code 會自動接收 Gemini 的 review 結果，它會接著分析、回應。Gemini 會把發現的每一個問題分成不同的嚴重等級，然後 Claude Code 會逐條回應：

- 有些它會承認：「這個確實是問題，我漏考慮了，修。」
- 有些它會 debate：「這個發現有道理，但在我們這個場景下不適用，因為...」
- 有些它會接受但降級：「這是一個 nice-to-have，不是 critical issue。」

這個過程讓我很驚喜。**兩個 AI 之間的張力，模擬了真實團隊裡作者和 reviewer 之間的健康對話。**

Claude 不是盲目接受 Gemini 的所有意見——它會辯護自己的選擇，但辯護的方式是講道理、給理由，而不是無條件合理化。Gemini 也不是永遠正確——有時候它確實挑了一些在當前場景下不重要的問題。但正因為有這層對話，最終留下來的 issue 通常都是真正值得修的。

這比讓 Claude 自己 review 好太多了。自己 review 的時候，它只會往「合理」的方向解讀；但面對一個外部的質疑，它反而能展現出真正的分析能力——是同意、是反駁、還是部分接受——每一個判斷都有具體的理由。

---

## 兩種 Review，各有位置

後來我把這個模式固定下來：每完成一個小任務，自動調用 Gemini review。Claude 收到 review 結果後分析回應，該改的改、該辯的辯，直到 fully approved。不需要我盯著，不依賴我的注意力。

但我也發現，不是每個場景都需要啟動這個完整流程。改了一行 typo 或加了一個 log，殺雞不需要用牛刀。所以我又做了 `code-review-claude`——一個用 Claude 自己做的快速 review，30 秒以內跑完，適合 50 行以下的小改動。

兩個 skill 各有各的位置：

- **日常小改動**：`code-review-claude`，快速掃一眼，確認沒有低級錯誤
- **功能開發、重構、任何超過 50 行的改動**：`code-review-gemini`，完整的獨立審查加上 Claude 的回應分析

這不是「多一個 AI」的問題，而是**把團隊 code review 的原則重新實作在 AI 工作流裡**：作者和 reviewer 分離、review 前移到每個小任務之後、而且 reviewer 的意見不是聖旨，而是需要被分析、被回應的 input。

---

## 帶走一件事

AI 自己 review 自己的 code 不是完全沒用——它確實會找到一些問題。但它找不到的那些問題，往往是更重要的。

試試看一個簡單的實驗：下次 Claude 寫完一段 code，不要問它「review 一下」。把同樣的 code 丟給另一個 AI（Gemini、GPT、甚至另一個全新的 Claude session），問同樣的問題。然後把結果拿回來，讓原來的 Claude 回應。

看看那場對話裡冒出了什麼——那些東西，就是你目前的 review 流程裡看不到的。
