# 當我開始信任 AI，事情開始出錯

> *這是「當 AI 越來越好用，品質反而越來越差」系列的第 1 篇。*
> *這一篇講的是：為什麼我花了三個月造了 32 個 AI skills，而不是直接用 AI 就好。*

---

2025 年的 AI Hackthon 之後，我開始認真用 Claude Code 寫程式。當初的參賽作品「Scam-Story AI」完全交給 Claude Code 包辦，我的角色應該是 PM 吧 ^^。

一開始很興奮。它能讀整個 codebase、理解上下文、一口氣產出幾百行可以跑的 code。我從來沒這麼快地交付過功能。幾天之內我就養成了一個習慣：寫需求、讓 AI 做、看起來對就合併。

一個月後，公司的專案。我在 review 自己的 repo 時愣住了。

那些 code 可以跑，但充滿了我不會寫的結構、我沒想過的假設、以及我不完全理解的邏輯。更糟的是，有些決策看起來合理——但其實建立在從未驗證過的前提上。問題不是 AI 寫了爛 code，問題是**我不知道哪些 code 是好的，哪些只是看起來好的**。

這是一個弔詭：AI 越好用，你越信任它，你就越少檢查。你越少檢查，品質就越難保證。

---

## 信任曲線

回想起來，我的信任變化大概是這樣：

**第一週：懷疑期。** 每行 code 都仔細看，每個建議都驗證。效率其實沒提升多少，因為我把省下來的時間都花在確認上了。但品質是好的。

**第二到三週：蜜月期。** 它做的幾次修改都是對的。我開始跳過某些 review 步驟。「上次這種情境它處理得很好，這次應該也沒問題吧。」產出速度飛快。

**第四週之後：放飛期。** 它已經變成我的 co-pilot，我變成了橡皮圖章。它說測試通過了？那就通過了。它說這個架構合理？那就合理。我的角色從「工程師使用工具」滑向「人類批准 AI 的決定」。

問題不是哪一天突然出事，而是一種**緩慢的品質侵蝕**。沒有一個 commit 是明顯的災難，但累積起來，codebase 的可預測性在下降。我開始看到一些 pattern：

- **可行性報告讀起來很完整，但假設沒有被驗證過。** 有一次我根據 AI 產出的技術評估投入了好幾天的開發，結果在實作中期發現底層技術根本不支援關鍵功能——那個限制從頭到尾沒被提過。
- **Code review 永遠是正面的。** 讓 Claude 回頭看自己剛寫的 code，它傾向解釋為什麼那些選擇是合理的，而不是真的挑毛病。就像叫一個人批改自己的作業一樣。
- **「完成了」不等於「對了」。** AI 很容易宣稱工作完成——測試通過了、功能實作了——但你追問下去會發現，它有時候根本沒跑測試，或者跑的測試不是你要驗證的那些。

每一個問題本身都不致命，但它們有一個共同的根源：**我把品質守門的責任交給了最不應該守門的角色——產出者本身。**

---

## 從修補到系統

意識到這件事之後，我的第一個反應是「那我更仔細地 review 就好」。但這個想法持續了大約三天。手動 review 不現實，而且我就是因為不想每行都看才用 AI 的。

真正的轉折是一個簡單的問題：**如果我不信任 AI 會自己維持品質，那我能不能讓品質變成流程的一部分，而不是依賴我的注意力？**

這就是 skills 的起點。

第一個 skill 很簡單——一個讓 Gemini（不是 Claude）來 review Claude 產出的 code 的流程。聽起來似乎有點荒謬，但邏輯跟真實團隊一樣：寫 code 的人不應該是唯一 review code 的人。用另一個 AI 不是因為它「更聰明」，而是因為它沒有對既有結構的認知偏見。但我認為用一個完全沒有背景知識的 Claude Code session 應該也有一樣的效果，所以後來我又做了一個用 Claude Code 審查代碼的 skill。

那個 skill 的確有效。它抓到了一些 Claude 自己 review 時會忽略的問題。

然後我想：技術可行性報告隱藏的問題呢？能不能建一個流程，強制在每份報告之後提取隱含假設、用代碼驗證最關鍵的那幾個？

然後是：能不能在 Claude Code 宣稱「完成」之前，強制跑一次驗證、確認輸出？

每一個問題都變成一個 skill。每一個 skill 都是把一條本來靠我記住的紀律，嵌入到 AI 的工作流程裡面。

三個月後，我有了 32 個 skills。

---

## 這個系列要講什麼

接下來的文章，我會把這段旅程拆開來講。

不是功能介紹。不是「這個 skill 的 YAML 長這樣」。而是每一個 skill 背後的**那個出錯的瞬間**——那個讓我覺得「不行，這樣下去不行」的具體事件，以及我怎麼把那個教訓變成一個可重複的流程。

大致分三段：

**第一段是踩坑。** 那份讓我浪費兩週的可行性報告、那次 AI review 自己 code 的鬧劇、那個「測試通過了」其實根本沒跑的事件。每篇一個故事，每個故事長出一個 skill。

**第二段是體系化。** 從修一個 bug 到建立一種思維。為什麼我讓 Gemini 審 Claude 的功課、為什麼我的研究流程要求先找反證、八個 skills 怎麼串成一條有閘門的管線。

**第三段是質變。** 同一個任務，有紀律跟沒紀律跑一遍，再看看差異。以及——如果你也想開始，你的第一步不是 clone 我的 repo，而是找到你自己的第一個痛點。

---

## 帶走一件事

如果你現在正處於**讓 AI 有紀律**之前的狀態——AI 越用越順、產出越來越快、但隱約覺得有什麼不太對——那個直覺是對的。

不對的不是 AI。不對的是你以為它會自己維持品質。

品質不是 AI 的預設行為，而是使用者要自己嵌進去的流程。這整個系列，就是在講怎麼嵌。
