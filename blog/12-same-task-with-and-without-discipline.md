# 同一個任務，有紀律 vs 沒紀律

> *這是「當 AI 越來越好用，品質反而越來越差」系列的第 12 篇，也是第三幕「質變」的第一篇。*
> *這一篇講的是：同樣一件事，有沒有 AI 紀律，結果差多少。*

---

前面 11 篇，我講了怎麼從踩坑開始，一步一步長出一套 skill 體系。概念講了很多，但你可能會問：**所以到底差多少？**

這一篇不講概念。我要拿一個真實的任務——code review——把「沒有 skill」和「有 skill」兩個情況攤開來比ㄧ比。

---

## Before：那些我審不動的 PR

我們組裡的分工是這樣的：每個人負責不同的模組，但大家開發的是同一個 app。所以 code review 的時候，你審的經常不是自己寫的那塊。

邏輯上這很合理——總不能拿去給 QA 或後端同事審吧，至少我們是同一個前端團隊。但實際操作起來，問題來了：**我得先理解他的邏輯，才能審他的代碼。**

我手邊永遠有自己的任務。花半小時去理解別人的設計脈絡，再花半小時仔細看邏輯漏洞——我實在沒那個餘裕。於是 PR 就這樣躺著。一天、兩天、三天。同事催了，我才硬著頭皮打開。

然後我做了一件每個忙碌工程師都會做的事：**只看表面。**

語法有沒有錯？風格一不一致？有沒有重複造輪子？「這段邏輯跟那邊的一樣，你可以抽出來做 utility。」——這種評論我給得出來，因為不需要理解他在做什麼，只需要看程式碼長什麼樣子。

但邊角案例呢？錯誤處理呢？效能瓶頸呢？這些要深入理解業務邏輯才看得出來的問題，我看不到。不是能力不夠，是**時間不夠**。

我知道這樣的 review 品質不好。但我能怎麼辦？不審嗎？更不行。隨便審？我已經在隨便審了。

---

## After：「幹！也抓太多錯誤了吧！」

有了 `code-review-gemini` 之後，事情變了。

同事丟 PR 過來，我不用再拖三天。因為 review 的第一步不再是「我得花半小時理解他在做什麼」，而是讓 skill 先跑一遍。

這個 skill 做的事情不複雜：把 diff 送給 Gemini，用我設計好的 review 框架去分析。框架裡有清楚的維度——邏輯正確性、邊角案例、錯誤處理、效能考量、可讀性。每個維度都有具體的檢查標準，不是那種「看起來 OK」的模糊判斷。

結果出來的那一刻，我知道規則變了。

它不只抓語法錯誤和風格問題——這些我本來就能抓。它開始指出**我看不到的東西**：這個 null check 漏了、那個 race condition 在特定時序下會出事、這段邏輯在 list 為空的時候會 crash。

這些都是邊角案例。以前我沒時間去想的那種。

我的同事收到 review 之後，回了一句我到現在都記得：

**「幹！也抓太多錯誤了吧！這也看得出來？」**

然後他就默默把問題修掉了。

---

## 不只是快，是能做到原本做不到的事

這裡有一個容易被忽略的重點：差別不只是速度。

如果 skill 只是讓我「更快做完同樣的事」，那它只是一個效率工具。但實際上發生的是——**它讓我做到原本做不到的事**。

以前我的 code review 只能覆蓋表面層（語法、風格、DRY）。現在它能深入到邏輯層（邊角案例、錯誤處理、效能）。這不是同一件事做得更快，而是**不同層次的事情**。

如果你把 code review 想成一座冰山：

- 水面上：語法、風格、命名、重複代碼——肉眼就能抓
- 水面下：邊角案例、race condition、錯誤處理缺失、效能瓶頸——需要深入理解才能發現

以前我只能處理水面上的部分。有了 skill，水面下的問題也浮出來了。

## 另一個場景：研究報告

Code review 不是唯一一個。

去年中我要為 Google Conference 2025 準備一份關於 AI 演進的分享。那時候還沒有 research pipeline 那套東西。我的做法是：上網搜一堆資料，丟進 Google NotebookLM，再丟進 Gemini 和 ChatGPT，讓不同工具幫我萃取值得分享的重點。

有 AI 嗎？有。有效率嗎？回頭看，真的沒有。

問題出在**沒有結構**。我在不同工具之間跳來跳去，每個工具給我一塊拼圖，但沒有人幫我把拼圖拼起來。哪些觀點互相矛盾？哪些資料來源可信度比較高？哪些是真正的趨勢、哪些只是炒作？——這些判斷全靠我自己在腦子裡整理。

如果是現在，我會用 `tech-research-pipeline` 跑一遍。八個階段、兩個 gate check、每一步都有明確的輸入和輸出。最後出來的不是散落的拼圖，是一份有結構的分析報告，包含正反觀點的比對和可信度評估。

這不是假設。是我後來在其他研究任務上實際走過的路線。差別大到讓我有點後悔當初為什麼沒有更早把這套東西造出來。（不過當時還沒有 Agent Skill 這種好物！）

## 所以「紀律」到底是什麼？

寫到這裡，我想釐清一個容易被誤解的概念。

「AI 紀律」聽起來很嚴肅，好像要你立下一堆規矩、照表操課。但其實沒那麼複雜。

紀律就是：**在你還沒有壓力的時候，先把品質標準寫下來。**

Code review 的時候，我沒有壓力——我又不是在修自己的 bug。所以我可以冷靜地想：一個好的 code review 應該看哪些面向？什麼叫做「看完了」？什麼叫做「只看表面」？

把這些標準寫成 skill，就是紀律。

**紀律不是約束你，是約束 AI。** 它讓 AI 不能只給你「看起來 OK」的回覆，而是必須按照你定義的品質標準來交差。

沒有紀律的 AI 協作像什麼？像請一個很聰明的實習生幫你做事，但你每次都只說「幫我看一下」。他會看，但他不知道你的標準，所以他的產出品質完全取決於他那天的判斷力。

有紀律的 AI 協作呢？像給這個實習生一份 checklist：必須檢查這五個維度、必須標注嚴重程度、必須給出改善建議。他的能力沒變，但你鎖住了品質下限。

---

## 帶走一件事

記得一句話：**有沒有紀律的差別，不在於 AI 的能力，而在於你有沒有把標準告訴它。**

AI 很聰明。但聰明不等於有品質。品質來自標準，標準來自你（以及前人）的經驗。

找一個你經常用 AI 幫忙的任務。問自己：「我有沒有明確告訴它什麼叫做做好了？」如果沒有，你就知道第一步該做什麼了。
