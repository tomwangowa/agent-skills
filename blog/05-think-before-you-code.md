# 想清楚再動手

> *這是「當 AI 越來越好用，品質反而越來越差」系列的第 5 篇，也是第二幕「長出體系」的第一篇。*
> *這一篇講的是：AI 最危險的能力不是寫錯 code，而是寫得太快。*

---

前四篇講的都是「AI 做錯了什麼」——報告有幻覺、review 有盲區、完成沒驗證。但第二幕要講的不一樣。從這篇開始，故事的主題從踩坑變成體系化：我怎麼把這些教訓變成一套可重複的思維方式。

第一個體系化的轉折，不是來自一個踩坑，而是來自一個「原來還可以這樣」的驚喜。

---

## 我本來以為已經很進階了

經歷了前面那些教訓之後，我發展出了一套自認為比較成熟的工作流程：

1. 我提出需求
2. 讓 Claude 寫一份 plan doc
3. 我同意之後，Claude 再寫 design doc
4. 我再同意，Claude 切分 tasks 寫成文件，附上 checklist
5. 然後開始實作

比起一開始的「叫 AI 做、看起來對就合併」，這已經進步很多了。至少有了明確的文件產出、有了審核節點、有了可追蹤的任務。

但這個流程有一個盲區：**plan doc 是 Claude 根據我的需求直接寫的。它假設我的需求已經是清楚的。**

大部分時候，我的需求並不清楚。我只是有一個方向、一個模糊的想法。Claude 拿到之後會幫我補齊細節——但那些細節是它假設的，不是我確認的。Plan doc 看起來完整，但裡面有多少是我真正想要的、多少是 Claude 自己填的，我其實分不清。

我沒有意識到這是個問題，直到我在 [superpowers](https://github.com/obra/superpowers) 這個開源專案裡看到一個叫 brainstorming 的 skill。

---

## 在 Plan 之前，還有一個步驟

superpowers 的 brainstorming skill 讓我驚為天人。

它做的事情概念上很簡單：在寫 plan 之前，先跟你**對話**。不是讓 AI 根據你的需求直接產出文件，而是讓 AI 一個問題一個問題地把你的想法問清楚。

這跟我原本的做法差在哪裡？差在**誰在主導需求的定義**。

我原本的流程是：我給一段需求描述 → Claude 產出 plan doc → 我審核。問題是，從需求描述到 plan doc 之間，Claude 做了大量的假設和補齊。我審核的時候，其實是在看「Claude 理解的版本」對不對，而不是在確認「我真正想要的是什麼」。

brainstorming 把這個順序翻過來：Claude 不做假設，它問問題。每個問題逼我把模糊的想法變成具體的答案。等問完了，**需求是我一個一個答案堆起來的，不是 Claude 替我猜的**。

我後來以 superpowers 的版本為基礎，改寫成自己的 `brainstorming` skill，加入了一些我覺得重要的調整。

規則是：

- **一次只問一個問題。** 不要一口氣丟五個問題讓我填表。一個一個來，根據我的回答決定下一個問題。
- **優先用選擇題。** 「你偏好 A 還是 B？」比「你想怎麼做？」更容易回答，也更容易收斂。
- **探索完需求後，提出 2-3 個方案。** 每個方案有明確的取捨分析和推薦理由。
- **等我確認之後才動手。** 沒有我的 approval，不准寫任何一行實作 code。

聽起來像是在拖慢速度？其實不是。大部分情況下，這段對話只需要 3-5 分鐘。但這 3-5 分鐘省下的，是後面可能浪費的幾個小時——做了再改、改了再砍、砍了再做。

而且這個過程經常讓我發現自己沒想清楚的地方。AI 問「這個通知需要即時還是可以延遲？」我才意識到我根本沒想過這個問題。這不是 AI 在質疑我，而是它在幫我把模糊的想法變成具體的 spec。

## CLAUDE.md：讓紀律變成預設值

但光有 brainstorming skill 還不夠。問題是：我什麼時候會記得用它？

答案是：我不會。特別是在興頭上的時候——「我想到一個好功能！」——我的本能是直接叫 AI 做，不是先叫它問我問題。

這就是 CLAUDE.md 的角色。

CLAUDE.md 是 Claude Code 的全局設定檔，你可以在裡面寫規則讓 AI 遵守。我在裡面加了一條：

> **Before implementing new features, invoke brainstorming skill.**

就這樣。從此以後，每次我說「幫我加一個什麼什麼」，Claude 不會直接動手，而是先啟動 brainstorming 流程。不需要我記住，不需要我自律。紀律嵌在設定裡，而不是靠我的記憶力。

這個模式後來變成我整個 skill 體系的基礎架構：**CLAUDE.md 負責路由（什麼情境觸發什麼 skill），skill 負責行為（觸發之後怎麼做）。** 就像你不會要求每個工程師記住所有的 CI/CD 規則，你會把規則寫在 pipeline 裡。同樣的道理，你不該要求自己記住所有的 AI 工作紀律，你應該把紀律寫在 CLAUDE.md 裡。

我的 CLAUDE.md 裡現在有十幾條這樣的路由規則：

- 遇到 bug → 觸發 `superpowers:systematic-debugging`
- 完成功能前 → 觸發 `completion-gate`
- 建立/修改 skill 後 → 觸發 `skill-auditor`
- 新功能 → 觸發 `brainstorming`

每一條都是一個曾經忘記而付出代價的教訓。

## 一個正在發生的例子

說起來有點 meta：你現在讀的這篇文章，就是 brainstorming skill 的產物。

這整個 blog 系列的設計——三幕結構、單篇模板、系列命名——都是在 brainstorming 流程裡一步一步問出來的。讀者是誰？目標是什麼？發文節奏？風格偏好？每個問題一次一個，每個回答影響下一個問題。

如果我跳過 brainstorming 直接說「幫我寫一篇關於 AI skills 的 blog」，我大概會得到一篇通用的技術文章——正確但無聊，完整但沒有我的聲音。

## 帶走一件事

下次你要叫 AI 做一個新功能，在按下 Enter 之前，試著先問自己：「如果有一個很聰明但完全不了解背景的工程師，他會先問我什麼問題？」

那些問題，就是你還沒想清楚的地方。

與其讓 AI 替你假設答案然後直接做，不如讓它先問你。3 分鐘的對話，省 3 小時的返工。
