# 那份看起來很完整的可行性報告

> *這是「當 AI 越來越好用，品質反而越來越差」系列的第 2 篇。*
> *這一篇講的是：一份 90 個引用的 AI 報告，怎麼讓我在不存在的 API 上規劃了六週。*

---

我們有一個微服務叫 SellerCheck，它的工作是抓 Amazon 的賣家評論，用來分析賣家是不是詐騙。底層用的是 nodriver 加上本地 Chrome 自動化——聽起來就知道不會長久。

2025 年底，Amazon 的防禦升級到了 TLS 指紋偵測和行為生物識別，而且把評論頁搬到了登入牆後面。我們的 FBN 只有 3 個固定 IP，一旦被封就全面停擺。這不是技術債，而是生存問題。

所以我用 AI 做了一份完整的技術評估：有沒有辦法把抓取邏輯遷移到雲端瀏覽器供應商（像 ZenRows 或 Bright Data），讓我們的 IP 永遠不直接接觸 Amazon？

---

## 那份報告

Gemini 交出來的報告讓我很滿意。

90 個引用來源。四階段部署路線圖。涵蓋了供應商比較、成本分析、風險評估。它甚至考慮到了 session 遷移的問題，建議用 `tab.set_local_storage(dict)` 預先填充帳號資料。

報告的核心方案很清楚：nodriver 可以透過 `uc.connect(browser_wsproxy=...)` 方法連線到遠端瀏覽器的 WSS 端點。這樣一來，本地不需要跑 Chrome，所有瀏覽器行為都發生在供應商的 IP 上。它描述了具體的程式碼路徑、API 呼叫方式、甚至預期的成功率（99-100%）。

另外，ScraperAPI 有一個專門的 Amazon Reviews API，可以直接回傳結構化 JSON，100% 成功率。

語氣極度自信。我讀完之後覺得，這不是一個「能不能做」的問題，而是「什麼時候開始」的問題。

所以我開始了。

---

## 六週後

Sprint 1 和 Sprint 2，我根據這份報告做了架構規劃，也完成了 ScraperAPI Product API 的 PoC 整合。那部分確實能跑——但有個小問題：原本我們一次能抓 30 到 150 則評論，現在 Product API 只回傳 5 到 15 則。評論量掉了 10 到 30 倍。

但真正的災難不是這個。

2 月中，我決定用一個新的方式重新審視這份報告——不是重讀報告本身，而是直接去讀 nodriver 的原始碼。

打開 `nodriver/core/browser.py`，逐行看。

`uc.connect(browser_wsproxy=...)` 這個方法不存在。

nodriver 的連線邏輯只支援 `host` + `port` 的組合，而且要求遠端提供一個 `/json/version` 的 HTTP 端點。它從來沒有支援過 `wss://` URL。我去查了 zendriver（nodriver 的一個分支），找到了一個 GitHub Issue #98——有人在問這個功能，但沒有人回應。這是一個未實作的 feature request，不是一個可用的 API。

然後我檢查了 ScraperAPI 的 Amazon Reviews API。因為 Amazon 登入牆的變更，那個端點已經標註「不可用」。

然後是 `tab.set_local_storage(dict)`。也不存在。nodriver 沒有這個方法。

報告裡的三個核心技術主張，全部是虛構的。

## 90 個引用，0 行原始碼

事後回想，最諷刺的不是報告錯了——AI 會犯錯，這不意外。諷刺的是**它錯得非常有說服力**。

90 個引用來源。每一個看起來都有出處。四階段路線圖，每階段有具體的程式碼片段。成本估算精確到小數點。如果你不打開原始碼去驗證，你完全有理由相信這份報告。

而我信了。六週。（註：這六週我還同時參與其他的專案）

問題的根源不是 AI 幻覺（雖然這確實是幻覺），而是**我的驗證流程有一個巨大的缺口**：我會讀報告、評估邏輯、檢查引用是否合理——但我不會去驗證那些看起來像是「事實」的技術主張。API 存不存在？方法簽名對不對？這些我預設是對的。

這就是確認偏誤最危險的形式：**不是你選擇性地忽略反面證據，而是你根本沒想到要去找。**

## 所以我造了三個 Skills

這次踩坑直接催生了三個 skill，它們後來成了我整個研究管線的基礎。

### tech-feasibility：結構化可行性評估

第一個改變是把可行性評估變成一個有固定步驟的流程，而不是讓 AI 自由發揮寫一份報告。8 個步驟，每個步驟有明確的輸入和產出。其中最關鍵的一步是：**列出這份評估依賴的所有技術假設，標記哪些是你驗證過的、哪些只是你相信的。**

如果當時有這個流程，「nodriver 支援 WSS 連線」就會被標記為一個未驗證的假設，而不是被包裝成一個事實。

### assumption-extractor：把隱含假設挖出來

第二個 skill 更進一步：它會掃描任何技術文件，系統性地提取裡面的假設——包括那些作者自己可能都沒意識到的隱含前提。每個假設被分為 CRITICAL、HIGH、MEDIUM、LOW 四個等級，CRITICAL 的假設如果被推翻，整個方案就不成立。

在 ScraperAPI 的案例中，「nodriver 可以連線到 WSS 端點」就是一個 CRITICAL 假設。如果在報告完成的那天就把它標出來，它會像紅燈一樣亮著，提醒我：這個還沒被證明。

### micro-poc-validator：用 30 行 Code 驗證假設

第三個 skill 是最直接的：挑出最關鍵的假設，用最少的代碼（通常不超過 30 行）實際跑一次。不是寫一個完整的 PoC，而是一個 5 分鐘的 spike——能不能連上？API 回傳什麼？方法存不存在？

如果當時有跑這一步，Day 1 的 5 分鐘就能發現 `uc.connect(browser_wsproxy=...)` 不存在。5 分鐘，不是 6 週。

## 帶走一件事

下次你拿到一份 AI 產出的技術評估，不管它看起來多完整、引用多少來源，問自己一個問題：

**這裡面有哪些技術主張，是我可以用 5 分鐘的代碼驗證的？**

如果你找到了但選擇不驗證——那你就不是在做技術決策了，你是在做信仰。
