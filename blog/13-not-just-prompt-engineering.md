# 不只是 Prompt Engineering

> *這是「當 AI 越來越好用，品質反而越來越差」系列的第 13 篇。*
> *這一篇講的是：從 prompt engineering 到 workflow design，槓桿點在哪裡改變了。*

---

## 從「不會跟 AI 聊天」開始

我剛開始用 ChatGPT 的時候，真的不太會聊。

丟一句話過去，回來的東西不是太泛就是離題。當時的模型確實也還在進步，但我自己問問題的方式也有很大的改善空間。

那陣子各家大廠都在推自家 LLM 喜歡的 prompt 格式。Zero-shot、few-shot、chain-of-thought⋯⋯名詞一堆，每個都有論文撐腰，每個都宣稱能讓 AI 表現更好。我花了一些時間研究，確實有用——但也確實很累。

每次要做一件事，我都得先想：「這次該用什麼格式？要不要給範例？要不要加角色設定？要不要指定輸出結構？」光是把問題問好，就花掉我一半的時間。

我心想：**這不對吧。我是要解決問題，不是要考 prompt 格式的試。**

---

## 所以我造了一個 Prompt 優化工具

既然手動寫 prompt 這麼累，那就讓 AI 幫我優化 prompt 吧。

我用 Streamlit 寫了一個工具叫 prompt-tool。概念很簡單：你隨便丟一句話進去——比如「幫我分析這張圖片是不是詐騙」——它會幫你分析這句話缺了什麼，然後生成一個有結構的、完整的提示詞。

老實說，效果蠻驚人的。隨便一句話都能被重新組織成有角色定義、有任務描述、有輸出格式、有約束條件的提示詞。我自己看了都嚇一跳，也介紹給同事用。

那時候我覺得：prompt engineering 的問題被我解決了。

---

## 但問題其實不在 prompt

回頭看，prompt-tool 解決的是**單次對話的品質問題**。你問一個問題，它幫你問得更好，AI 回答得更好。沒毛病。

但我後來遇到的問題，不是「單次對話品質不好」。

是 code review 品質不穩定。是研究報告缺乏結構。是同一個工作流程每次做的品質都不一樣。是跨 session 的記憶斷裂。是 AI 不知道什麼時候該停下來驗證。

**這些問題，你給再好的 prompt 也解決不了。**

因為它們不是「怎麼問」的問題，是「怎麼做」的問題。不是輸入端的問題，是流程的問題。

---

## 一個意外的轉折：prompt 變成了 skill

後來公司內部辦了 PM Skill Workshop，我想找一個好的切入點讓大家理解什麼是 AI skill。我想到了 prompt-tool——先讓大家看看自己平常寫的 prompt 有多粗糙，經過優化後變成什麼樣，這個對比夠震撼。

為了教學，我在 prompt-tool 上加了一個功能：**Convert to Skill**。把優化後的 prompt 轉換成一個可重用的 Claude Code skill。

功能寫得不算好，但它意外地讓我看清了一件事：

**prompt 是一次性的。skill 是可重用的。**

一個好的 prompt 能讓這一次的對話品質很高。但下一次呢？你得重新寫一個好的 prompt。或者從歷史紀錄裡翻出上次的 prompt，然後手動調整。

而一個 skill 呢？你寫一次，之後每次觸發都用同樣的標準。code-review-gemini 不會因為你今天很忙就只看表面。completion-gate 不會因為你趕時間就跳過驗證。

**Prompt 管的是一次對話。Skill 管的是一類任務。**

這就是槓桿點的轉移。

---

## 槓桿在哪裡？

如果要我畫一條線，大概是這樣的演化：

**寫更好的 prompt** → 讓單次對話品質更好
↓
**造工具優化 prompt** → 降低寫好 prompt 的門檻
↓
**把 prompt 變成 skill** → 讓品質標準可重用
↓
**設計 workflow（pipeline、gate、role）** → 讓多步驟任務有結構
↓
**管理 skill 體系（router、auditor）** → 讓整套系統可維護

每一步的槓桿效果都比上一步大。但有趣的是，大部分人停在前兩步。

社群裡的討論已經開始轉向了——越來越多人在聊 skills、harness design、agent workflow。但據我所知，還有部分同事對 AI 的認知還停留在「怎麼跟 AI 說話」。

不是說 prompt 不重要。它是基礎。但如果你只優化 prompt，就像只調整問問題的方式，卻不改變做事的流程——你能改善的幅度有限。

---

## 我自己差點也困在那裡

說一個有點尷尬的事：在造 skill 體系之前，我還打算寫一個叫 **Context Engineering Studio** 的東西。

概念很酷——幫你管理給 AI 的 context，讓每次對話都有最完整的背景資訊。但我一直搞不清楚受眾是誰、痛點是什麼、具體該怎麼做。想了一陣子，不了了之。

現在回頭看，我知道為什麼了。因為我當時還在用**輸入端的思維**思考問題。「如果我能給 AI 更好的 context，它就能做得更好」——這個邏輯沒錯，但它只是一半的答案。

另一半是：**就算 context 完美，如果沒有流程約束，AI 的產出品質還是不穩定。**

完美的 context + 沒有流程 = 每次都很好，但每次好的方式不一樣，你無法預測和標準化。

**普通的 context + 好的流程** = 每次品質穩定在一定水準以上，而且可以持續改進。

我寧願選後者。

---

## 帶走一件事

Prompt engineering 是起點，不是終點。

如果你還在研究怎麼寫出完美的 prompt，很好，繼續。但同時問自己一個問題：**「這件事我下次還會做嗎？」**

如果會，那你需要的不是一個更好的 prompt，而是一個 skill。

如果這件事涉及多個步驟，那你需要的不是一個 skill，而是一個 workflow。

把注意力從「怎麼問」移到「怎麼做」。
