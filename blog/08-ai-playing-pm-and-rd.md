# 當 AI 開始扮演你的 PM 和 RD

> *這是「當 AI 越來越好用，品質反而越來越差」系列的第 8 篇。*
> *這一篇講的是：我怎麼讓 AI 同時扮演 PM 和 RD，以及為什麼它們必須「互相看不見」。*

---

前幾篇講的都是研究和驗證——怎麼確保 AI 做的研究是可靠的。但軟體開發不只有研究。在動手寫 code 之前，你通常需要兩件事：搞清楚要做什麼（需求），和搞清楚怎麼做（設計）。

這兩件事，我以前都是自己做的。或者更準確地說，我以為我在做，但其實我跳過了大部分。

---

## 一個人的需求分析

我是工程師。我的自然反應是：有了想法，就開始想怎麼做。

「需求」？我腦子裡有個大概的方向就夠了。「設計」？邊寫邊想。這在小專案上沒問題——一個人開發、一個人用，需求就是你自己想要的東西，設計就是你寫出來的 code。

但當專案稍微大一點，這個模式就開始出問題。

我發現自己經常寫到一半才卡住：這個欄位要不要必填？這個錯誤狀態要顯示什麼訊息？這個 edge case 要不要處理？這些問題不難，但每一個都是我在寫 code 的時候才第一次想到的——然後我就自己猜一個答案，繼續寫。

猜的答案有時候對，有時候不對。不對的時候就要改，甚至重來。

---

## 讓 AI 拆成兩個人

第 5 篇講到 brainstorming——在動手之前先讓 AI 問你問題。那已經比直接做好很多了。但 brainstorming 產出的是一個設計方向，不是完整的需求文件和技術設計。

我想要的是一個更結構化的流程：先有人把需求整理清楚，然後另一個人根據需求做技術設計。

關鍵是「另一個人」。

為什麼需要兩個角色，而不是讓同一個 AI 先寫需求再寫設計？因為**角色會汙染思考**。

如果你讓同一個 AI 先扮演 PM 寫需求、再扮演 RD 寫設計，它在寫需求的時候就已經在想實作方式了。「這個需求用 Redis 很好做」——於是需求就不知不覺地被實作方式塑造了。PM 應該想的是「使用者需要什麼」，不是「什麼好做」。

所以我用了 subagent——每個角色跑在一個獨立的 AI agent 裡，彼此看不見對方的思考過程。

PM agent 只知道使用者的目標和限制，它產出需求文件。RD agent 只看到 PM 的需求文件和技術限制，它產出技術設計。它們之間唯一的溝通管道是我——我審核 PM 的產出，同意之後才交給 RD。

這個隔離不是技術上的需要，是**認知上的需要**。

---

## 不是每個專案都需要寫 PRD

一開始設計這個系統的時候，我遇到了一個明顯的問題：如果每個專案都要跑完整的 PM → RD 管線，那修一個小 bug 也要先寫需求文件嗎？

當然不是。所以我加了 project size calibration。

管線會根據專案大小調整產出的深度：

**小專案**（一個人、兩週內）：PM 產出的是一頁 bullet list——幾個需求、每個有驗收條件、一段 scope 說明。RD 產出的是 inline code plan——元件清單、關鍵函式、資料流。整個流程 20 分鐘。

**不小的專案**（3-5 人、一兩個月）：PM 寫 user stories 搭配 Given/When/Then 驗收條件、MoSCoW 優先級。RD 做 component diagram、完整的 API spec、story point 估算。

我不談**大專案**（6+ 人、兩個月以上）：那不是我這個層級要做的事。

同一條管線，不同的精細度。小專案 20 分鐘跑完，不小的專案花久一點但也不至於變成寫文件大賽。

---

## 又是 Gate

跟第 7 篇的 research pipeline 一樣，這條管線也有 Gate。

**Gate A** 在 PM 階段之後：我審核需求文件。不合適就打回去修改，最多三輪。

**Gate B** 在 RD 階段之後：我審核技術設計。

但這裡有一個 research pipeline 沒有的步驟：**Convergence Check**。

Gate B 之後，管線會自動比對 PM 和 RD 的產出：

- PM 的每一條需求都被 RD 的設計覆蓋了嗎？
- RD 有沒有偷偷加了 PM 沒要求的東西？
- RD 有沒有因為技術原因砍掉了某些需求？

如果 RD 砍了需求，管線不會阻止它——但它會把這件事攤出來：「RD 把需求 X 從 scope 裡移除了，理由是 Y。你同意嗎？」

這解決了一個微妙但重要的問題：**沉默的 scope 變更**。當同一個人（或同一個 AI session）同時做需求和設計的時候，需求會在不知不覺中被修改以配合實作。而且因為沒有人在對照，你甚至不知道需求被改了。

兩個獨立的角色 + 一個 convergence check，讓這種沉默的變更變成顯式的決定。

---

## 所以我造了這個

`role-orchestrator` 是指揮官，`role-pm` 和 `role-rd` 是兩個角色。

```
使用者的目標
   │
   ▼
Phase 0: 載入 project profile（大小、優先級、技術棧）
   │
   ▼
Phase 1: 派遣 PM subagent → 需求文件
   │
  Gate A: 我審核需求
   │
   ▼
Phase 2: 派遣 RD subagent → 技術設計
   │
  Gate B: 我審核設計
   │
   ▼
Phase 3: Convergence Check → 對齊報告
   │
   ▼
Phase 4: 下一步（寫 plan、繼續探索、或直接開始 coding）
```

Orchestrator 的規則很明確：它只負責協調，不負責思考。它不會自己做 PM 或 RD 的分析——每個角色的思考都發生在隔離的 subagent 裡。

PM 的規則也很明確：**stay in your lane**。PM 不做技術決策。它可以說「這個可能很複雜」，但不能說「用 Redis 做」。反過來，RD 不發明需求——它拿到 PM 的需求文件，照著做設計。如果它覺得某個需求技術上不可行，它要明確寫出來，而不是偷偷繞過去。

每個角色都有自己的限制。這些限制不是束縛，是品質保障。

---

## 一個人也能有分工

你可能會想：我一個人開發，搞什麼 PM 和 RD？`role-planner` 和 `role-developer` 也可以。

但重點不是人數，是**思考模式的切換**。

當你同時想「使用者需要什麼」和「技術上怎麼做」的時候，這兩種思考會互相干擾。你會不自覺地把需求往技術上好做的方向靠，而不是往使用者真正需要的方向走。

把它拆成兩個階段，即使兩個階段都是 AI 在做，你在中間審核的時候會更清醒——因為你每次只需要判斷一件事：「這個需求對嗎？」或「這個設計對嗎？」，而不是同時判斷兩者。

---

## 帶走一件事

下次你要開始一個新功能，試著在腦子裡（或用 AI）把兩個問題分開回答：

1. **使用者需要什麼？**（不要想怎麼做）
2. **技術上怎麼做？**（基於第一步的答案）

光是這個順序——先 what，再 how——就能避免很多「做了才發現不是使用者要的」的浪費。

不需要 subagent，不需要管線。意識到這兩種思考需要分開，就已經是最重要的一步了。
