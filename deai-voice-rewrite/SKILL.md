# 去 AI 味 ＋ 白話 ＋ 貼 Tom 口吻 改寫

這個 skill 只做一件事：把 **Tom 要對外發表的稿**（簡報稿、blog、newsletter、貼文）改成「不像 AI 寫的、白話、聽起來就是 Tom 本人在講」。

它**只動語氣與用詞**，不動內容。改寫的鐵律是：**事實一個字都不能漂、語意一個字都不能被你「順手糾正」。** 這兩件事是這個 skill 存在的理由，違反任何一條，再漂亮的潤稿都是失敗品——下面兩道 guard 會把它變成每次都要交出的產出物，不是口號。

> **使用前提**：純 on-demand。Tom 明確叫用才跑，不要做成 hook、不要設成自動關卡。
>
> **與 output-style 的分工**：這個 skill 負責「**改一份既有的稿**」（帶事實凍結 / 語意凍結兩道 guard）。若要規範「**AI 之後所有回應的講話方式**」，那是 companion output-style `deai-tom`，用 `/config` → Output style 開關。它的真檔版控在本 repo 的 `output-styles/deai-tom.md`，live 路徑 `~/.claude/output-styles/deai-tom.md` 是指回來的 symlink。兩者共用同一套去 AI 味規則——這份 SKILL.md 是規則的**單一真相來源**，output-style 會回頭指向這裡。

## 開工前先確認（Step 0）

動筆前先問清楚，不要猜：

1. **改哪一份／哪一段？** 對外用途是什麼（簡報稿 / blog / newsletter / 貼文）？對象是誰（工程師？一般同事？）——這會決定「哪些專名要白話解釋、哪些不必」。
2. **有沒有要補餵的近期樣本？** Tom 可以丟幾篇近期寫的東西，讓你抓「當下這陣子」的語氣，疊在內建 profile 上微調（見最後一節）。沒有就用內建 profile。

---

## 固定流程

照順序走，不要跳。Guard 1 的「列 token」一定要在改寫**之前**做，否則改完才回頭找事實漂移會漏。

1. **讀原文。** 若 Tom 提供了近期樣本，先讀樣本、抓當下語氣特徵，疊加到 `references/tom-voice-profile.md` 上。
2. **列受保護 token（Guard 1 前置）。** 掃一遍原文，把所有「事實層」的東西列成清單（見 Guard 1）。這份清單等一下要當核對表。
3. **套去 AI 味規則 ＋ 對口吻。** 用下面的規則改寫，同時讓它聽起來像 Tom（profile 是「傾向」，不是逐段打勾的檢查表——見口吻那節）。
4. **標記可疑語意（Guard 2）。** 改寫過程中遇到「看起來怪、像錯字、像用錯詞」的地方，**不要改**，丟進「需要你確認」清單。
5. **產出三件套。** 改寫稿 ＋ 事實凍結 checklist ＋ 需要你確認清單（見「輸出格式」）。
6. **改寫後逐項核對事實凍結。** 拿 Step 2 的 token 清單，逐項確認每個 token 在改寫稿裡都還在、且一字未變。

## 去 AI 味規則

> **基準：以 Tom 的 brief 為準（嚴格版）。** Tom 已核可過的成品（gold file）是觀察「他口吻」的最佳證據，但在下面這幾條規則上，Tom 明確選擇用「比成品更嚴格」的標準。所以規則照 brief 嚴格寫，**口吻**照成品學。

### 1. 戰爭隱喻全清
作戰、戰場、被殺、淪陷、攻防、火力、對付 → 換成平實動詞（處理、應對、面對、解決、一種對應一種解法）。
- **注意**：連語氣較輕的「對付」也要換掉。Tom 的成品其實留了「對付」，但他在 brief 裡選擇連這個都清掉——照 brief。
- ❌「先看我每天的**戰場**」「效率跟信心同時**被殺**」「一根**對付**一種」
- ✅「先看我每天實際碰到的狀況」「時間就這樣被吃掉，信心也跟著動搖」「一根**處理**一種」

### 2. 「不是 X，是 Y」對仗句：每段／每頁最多留 1–2 處
這種對仗句拿來強調很有力，但 AI 會無限濫用、變成腔調。**每個段落／每張投影片（沒有分頁就每個小節）最多留 1–2 處當真正的強調，其餘一律改寫**——軟化成「其實比較像…」「真正的關鍵是…」，或拆成兩句講。
- **為什麼用「每段／每頁」而不是「全文」**：長文（例如 23 頁講稿）沒辦法可靠地數完整份的對仗數，「全文 1–2」實務上無法稽核、容易變成各段各留各的、整份超標。改用「每段／每頁」這個你掃得完的單位，才套得動。
- ❌（每段都來一次）「不是 A，是 B」
- ✅ 軟化：「其實不是我比較會下指令，**而是**我把…清掉了」／拆句重講

### 3. 罐頭句尾與標題：禁止重複模板
最典型的 AI 病：每段結尾都來一句一模一樣的「**可偷走的招式：**」。**同一個模板句只要出現第二次就是病。** 要保留的重點，每次用**不同的自然句**帶出，而且不是每段都要收尾。
- ❌ 每段「可偷走的招式：…」
- ✅ 每處都不同：「所以這招你也可以拿去用」「我自己的心得是」「我的建議是」「先試一種就好」——有些段落乾脆不收尾

### 4. 台灣慣用詞
遇到中國大陸／AI 慣用詞，換成台灣工程圈的講法。常見對照：

| AI／陸用 | 台灣工程圈 |
|---|---|
| 代碼 | 程式碼 |
| 信息 | 資訊 |
| 質量（品質語境）| 品質 |
| 缺省 | 預設 |
| 視頻 | 影片 |
| 調用 | 呼叫 |
| 文件（程式語境）| 檔案 |

⚠️ 換詞前先看語境——「質量」在物理語境是對的、「文件」在公文語境是對的。語境不確定就走 Guard 2 標記，不要硬換。

### 5. 口頭禪節制 ＋ AI 慣用詞黑名單
反覆出現的口頭禪（最常見：**痛點**）盡量不用，或變化講法——痛、最痛的、頭痛、麻煩。同一個詞在一段內出現第三次，就該換。（別用「卡住」——見 profile §8 避用詞。）

AI 慣用詞黑名單（Tom 看到立刻辨認是 AI）：**協助**（對外稿用「幫我／幫你」或省略）、**還行**（模糊敷衍，換成直接陳述狀態）、**很穩**、**拍板**、**收斂**、**踩到**。

### 6. 專名第一次出現就白話解釋——但別浪費篇幅
判準只有一句：**目標讀者會不會讀不下去？**
- 第一次出現、或不解釋就看不懂的專名 → 補**一句**白話。例：mock→「一個假的替身」、harness→「事先替 AI 搭好的工作架子」、Snowflake→「一種數字型的唯一識別碼」、orphan→「孤兒資料」、dry-run→「先空跑一遍」、drift→「飄移」、symlink→「捷徑連結」。
- 工程師本來就懂的（DB、CI、API、commit、schema、Postgres…）→ **不要解釋**，浪費篇幅又像在說教。
- 對象若是非工程師，門檻放低；對象是 RD，門檻拉高。

### 7. 把壓縮、跳太快的句子展開成完整白話——但不灌水
AI 愛把三步併一句、邏輯跳著走。展開它，補上中間被省掉的環節。
- **判準：每一處展開都要「買到」東西**——買到一句名詞解釋，或買到一段被跳過的邏輯。買不到任何東西的展開就是灌水，刪掉。
- 這條會讓字數變多（Tom 的成品講稿字數普遍變多），這是對的；變多但每個字都有用，才叫白話，不叫膨脹。

### 8a. 不要中英夾雜（這太「工程師腔」，Tom 不喜歡）
中文句子裡塞英文單字當填充詞，是最典型的工程師寫法，對外稿要清掉。英文詞分三類處理：
- **A. 字面 identifier／API 欄位／設定值（東西的「名字」）→ 凍結，一字不動。** 服從 Guard 1，翻了就錯。例：`access_token`、`refresh_token`、`offline_access`、`BACKEND_API_URL`。
- **B. 已成標準的技術專名，翻成中文反而更難懂 → 保留英文，第一次出現依規則 6 補一句白話。** 例：OIDC、OAuth、API、endpoint、scope、token、staging。
- **C. 一般英文被當口頭填充詞、明明有自然中文 → 一律翻成中文。** 這就是要殺的「工程師腔」：
  - try try 看 → 試試看；follow 這個規範 → 遵守／照這個規範走
  - user → 使用者；response → 回應／回傳的內容；request → 請求
  - check／confirm → 確認；support → 支援；issue → 問題；Hi → 大家好
  - approach → 方向；work（作動詞）→ 行／可行；awkward → 尷尬
- **判準一句話**：「這個英文詞換成中文會更難懂、或它根本是個名字嗎？」會／是 → 留（A 凍結、B 保留＋首次白話）；不會 → 翻（C）。
- **同一概念的「講法」和「名字」要分開**：prose 講「refresh token」屬 B（保留）；欄位名 `refresh_token` 屬 A（凍結）——別因為翻了前者就動後者。

### 8b. 全形標點
中文文字裡的標點統一全形（，。！？「」……），不與半形混用。代碼及識別字內部的標點不受此限。

### 9. 列點節制
被問「有哪些 X」「都做哪些」這類誘發列舉的問題，最多列 1–2 項；真的有更多，先講最重要一項＋一句「其他還有幾個」帶過。列完**不加比較評語收尾**（「比 XX 好多了」是明顯 AI 破綻——2026-07-02 Turing test 教訓）。

### 10. 避免工整對仗句
「A 是⋯，B 也是。」這類前後結構完全對稱的書面句型，讀起來太 AI（2026-07-02 Turing test 中被抓包的案例：「Peter 是萬花筒認識的，ShuHan 也是。」）。改用口語、不對稱的講法，或用「都」字合併但不重複相同動詞結構。

詳細的 before/after 教材（取自真實 gold-standard diff）在 **`references/examples.md`**，改寫前讀一遍能抓到手感。

## Tom 口吻 profile

完整 profile 在 **`references/tom-voice-profile.md`**，**每次改寫都先讀它**（它會隨 Tom 補代表作而長大）。核心特徵：

- **軟開場**：「我有個想法，就是…」「先講一個我想了很久才想通的點」
- **大量限定詞**：我覺得 / 倒是覺得 / 據我所知 / 見仁見智 / 理論上 / 老實說 / 其實 / 大概 / 不太
- **坦白講不確定**：「我不知道有什麼方法可以…」「我自己也還沒做完」「我不敢讓 AI 直接下手」
- **破折號 `——` 和「」** 鋪陳、強調概念
- **隨口收尾**：「…就是了」「…就好」
- **不誇張、不喊口號、不用排比金句**；把「誠實、講清楚限制」當賣點（誠實 ≠ 扣分）
- **直接對讀者說「你」**

> **最重要的一條：口吻是「傾向」，不是「每段必中的檢查表」。** Tom 的成品是**克制**的——他不會每一段都塞滿「老實說 / 其實 / 就是了」。硬要每段命中這些 marker，產出的是「假 Tom」，比 AI 味更糟。讓這些特徵自然浮現，密度比照他的真實成品。

## Guard 1：事實凍結（每次都要交 checklist）

改寫只動語氣與用詞。**以下這些東西一個字都不准動、不准翻譯、不准改格式、不准「修正」：**

数字、port、URL、檔名／路徑、識別字（如 `account_id`）、表名／schema 名、code span、英文 API／指令名詞（`/api/reset`、`BACKEND_API_URL`…）、md5／hash、人名／專名／代稱。

**做法：**
1. 改寫**前**（Step 2）把這些 token 全列出來。
2. 改寫**中**原樣保留。
3. 改寫**後**（Step 6）逐項核對。
4. 輸出時附一張 **事實凍結 checklist**，每個 token 標「原值 → 改寫稿中仍存在且未變 ✅」。

成品就是這樣——`127.0.0.1:8080`、`:9000`、`md5: a1b2c3d4`、十幾張表、`account_id` 18 位…全部一字未動。skill 每次也要證明它做到了，不是嘴上保證。

## Guard 2：只改語氣，不改語意（flag-don't-fix）

**這是這個 skill 最重要的紀律，也是最痛的血淚教訓。**

看起來怪、像錯字、像用錯詞、像可疑的地方——**極可能是刻意的，或有專屬含義**。你**不准自作主張改**。把它丟進「需要你確認」清單，附上：原文、為什麼可疑、你猜的兩種解讀、建議。等 Tom 裁示再動。

### 招牌範例：「小薇」事件（真實事故，已匿名；務必理解這個再開工）

某個領域 skill 的 SKILL.md 裡寫「雙寫順序：先寫上游、後寫 **小薇**」。

- 一個「樂於助人」的 editor 會覺得「小薇」很怪——是不是打錯了？是不是某個系統？於是「順手」把它改掉或解釋成某個服務。
- **真相**：「小薇」（化名）是作者**同事的名字**，她負責 agent DB 那一塊，所以作者在對話與 skill 裡用她的名字當 agent DB 的**口語代稱**。
- 結果：editor 改錯 → 作者發現 → 解釋 → 又改錯一次 → 來回兩趟。
- **正解**：對外讀者不認識「小薇」，照字面留著會被誤解成某個系統，所以**對外稿一律寫 `agent DB`**——但這是**語意決定，要作者拍板**，不是 editor 自己判斷後默默改掉。

教訓一句話：**遇到「怪」，先停手、標記、問。不要猜，更不要默默改。**

```
## 改寫稿
<完整改寫後的內容>

## 需要你確認（語意層）

## 改了哪些、為什麼（可選，重點摘要）

```

## 樣本微調（補餵近期樣本）

內建 profile 是底。Tom 可在執行時丟幾篇近期寫的東西，讓你抓「**這陣子**的語氣」疊上去微調：

- 讀樣本，抓**當下**的高頻語氣特徵（這次特別愛用哪些開場、收尾、限定詞、句長）。
- 疊在內建 profile 之上：衝突時以**近期樣本**為準（人是會變的）。
- 這只影響本次改寫，不會改 `references/tom-voice-profile.md`。
- 若 Tom 說「這幾篇拿去精修 profile」，才把萃取結果寫回 `references/tom-voice-profile.md`。

## 別做的事（反面教材）

- ❌ 自動跑 / 設成 hook / 設成 pre-commit 關卡——這是 on-demand 工具。
- ❌ 為了像 Tom 而每段硬塞口吻 marker（假 Tom）。
- ❌ 改數字、改檔名、改識別字（破壞 Guard 1）。
- ❌ 看到怪詞默默「修正」（破壞 Guard 2）。
- ❌ 灌水式展開——展開要買到名詞解釋或被跳過的邏輯，否則刪。
- ❌ 把同一個收尾模板用第二次。
